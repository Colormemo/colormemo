# ColorMemo

Веб-приложение для тренировки зрительной памяти и цветового восприятия.
Учебный проект по дисциплине «Управление программными проектами», Московский Политех, группа 231-334.

**Команда:** Ксюша (аналитик, тимлид) · Соня и Катя (дизайн) · Настя и Маша (разработка)

## Что умеет

План-минимум из лабораторной 1 закрыт целиком:

- **две игры** — «Выбери цвет» и «Повтори цвет», по пять заданий в серии;
- **два уровня сложности** — отличаются временем показа и тем, насколько близки варианты;
- **регистрация и вход**, сессия на подписанной httpOnly-cookie;
- **сохранение результатов**, история прохождений и личные рекорды в профиле;
- **статистика** — число попыток, средняя точность и лучший результат по каждой игре и уровню.

Играть можно и без аккаунта, но тогда результаты никуда не записываются.

## Из чего собрано

| Слой                | Технология                | Почему                                                    |
| ------------------- | ------------------------- | --------------------------------------------------------- |
| Фронт               | React + Vite + TypeScript | Быстрая сборка, типы ловят ошибки в структурах заданий    |
| Выбор цвета         | react-colorful            | Готовая пипетка на 3 КБ                                   |
| Цветовая математика | culori                    | Перевод в Lab и Delta E 2000                              |
| Бэк                 | Express + TypeScript      | Тонкий API, проверка входящих данных через zod            |
| База                | PostgreSQL + Prisma       | Реляционная, как в лабе 1; миграции одной командой        |
| Пароли и сессии     | node:crypto               | scrypt и HMAC из стандартной библиотеки, без зависимостей |
| Общий код           | Пакет `@colormemo/shared` | Типы и формулы описаны один раз на двоих                  |

Внешних библиотек для авторизации нет сознательно: нужен ровно один алгоритм хеширования и один — подписи, это пара десятков строк на `node:crypto`. Заодно отпала нативная сборка argon2, которая на Windows требует отдельно поставленных средств компиляции.

## Первый запуск

Нужен [Node.js 22](https://nodejs.org/). Для работы с настоящей базой — ещё [Docker Desktop](https://www.docker.com/products/docker-desktop/).

```bash
git clone <адрес репозитория>
cd colormemo

npm install                       # зависимости всех пакетов сразу
npm run build:shared              # общий пакет надо собрать первым

cp backend/.env.example backend/.env
```

Дальше — один из двух вариантов.

### С базой (как в настоящей работе)

```bash
docker compose up -d                              # база на 5433 + Adminer на 8080
cd backend && npx prisma migrate deploy && cd ..  # применить миграции
cd backend && npx prisma db seed && cd ..         # справочник игр
```

Затем в двух терминалах:

```bash
npm run dev:back     # http://localhost:3000
npm run dev:front    # http://localhost:5173
```

### Без базы

Если Docker не поднят, приложение работает целиком — пользователи, результаты и статистика пишутся в файл `backend/.data/colormemo.json`:

```bash
npm run dev:nodb     # вместо npm run dev:back
npm run dev:front
```

Это не замена базе: файл не рассчитан на нескольких одновременных игроков. Он нужен, чтобы разрабатывать и показывать проект там, где Postgres не поднят.

### Всё приложение одной командой

```bash
docker compose --profile full up -d --build    # затем http://localhost:3000
```

Так оно и работает у пользователя: один сервер отдаёт и сайт, и API.

### На Windows (Настя)

Отдельная инструкция со всеми шагами: [docs/setup-windows.md](docs/setup-windows.md).

Коротко: ставятся Node 22, Git for Windows и Docker Desktop, работа идёт в PowerShell либо в WSL. Обязательно один раз выполнить `git config --global core.autocrlf false`, иначе переносы строк разойдутся с macOS.

## Проверки

```bash
npm test               # 13 тестов: цветовая математика и подсчёт точности
npm test -w backend    # 44 теста: ручки API поверх хранилища в памяти
```

Тесты бэка поднимают настоящее приложение Express и ходят в него запросами, но хранилище подставляют в памяти — поэтому Postgres для них не нужен ни локально, ни в CI. Это ровно то, ради чего хранилище описано интерфейсом (`backend/src/games/repository.ts`), а не вызовами Prisma из игровой логики.

Что покрыто: выдача заданий и границы уровней, подсчёт точности и очков, запрет повторного ответа, регистрация и вход (включая одинаковый ответ на неверный пароль и на несуществующий логин), подделка cookie, изоляция статистики разных игроков.

## Как мы договорились работать

**Ветки.** В `main` не пушим напрямую. На каждую задачу своя ветка: `feature/game-color-choice`, `feature/auth`, `fix/timer-reset`. Дальше пул-реквест — чтобы изменения было видно одним списком и чтобы на них прогналась проверка кода. Обязательное одобрение мы сняли: мержит та, кто открыла пул-реквест, ждать второй не нужно. Если правка задевает чужую зону или `packages/shared` — всё равно показываем до слияния.

**Разделение зон** (по лабе 4). Савельева — клиентская часть: окружение фронта, маршрутизация, интерфейсы игровых экранов, профиль и статистика на стороне клиента. Володина — серверная часть: проект сервера и PostgreSQL, модели данных, расчёт точности, сохранение результатов, проверка игровой логики.

В играх зоны делятся внутри одной задачи: логика и расчёты за Володиной, интерфейс за Савельевой. Стык — `packages/shared`: любую правку контракта обсуждаем до кода, потому что она ломает работу обеим.

**Регистр в именах файлов.** Компоненты — `PascalCase.tsx`, остальное — `kebab-case.ts`. Импорт пишем ровно так, как называется файл. На маке и Windows регистр не важен, а на Linux (в контейнере и на GitHub) важен — иначе сборка развалится там, где мы этого не увидим.

**Параметры игр.** Только в `packages/shared/src/difficulty.ts`. Никаких «магических» чисел в компонентах: после тестирования на людях баланс придётся крутить.

## Безопасность, коротко

Что сделано и почему — пригодится в разделе рисков:

- **пароли** хранятся только как результат scrypt со своей солью у каждой записи; сам пароль не пишется ни в базу, ни в логи;
- **сессия** — подписанный HMAC-SHA256 токен в httpOnly-cookie: скрипт страницы до неё не дотянется, а подделать её без секрета нельзя;
- **ответ на вход** одинаков для неверного пароля и несуществующего логина, и время ответа в обоих случаях совпадает — иначе перебором можно узнать, какие логины заняты;
- **очки считает сервер** по сохранённому у себя заданию: клиент присылает только свой ответ, подменить результат через консоль браузера нельзя;
- **всё, что приходит от клиента**, проходит через zod — включая уровень сложности, который иначе можно было бы задрать правкой запроса;
- **секрет подписи** обязан быть задан: с `NODE_ENV=production` сервер не стартует со значением из примера.

Чего сознательно нет: восстановления пароля (некуда слать письмо), ограничения числа попыток входа и журнала действий. Для учебного проекта это осознанно оставлено за рамками, а не забыто.

## Публикация

### Один домен, один сервер

Сайт и API живут на одном адресе: сервер отдаёт `/api/...`, а на всё остальное — собранный фронт. Из этого следует три вещи, которые сильно упрощают жизнь:

- **CORS не нужен вообще** — браузер считает запросы своими;
- cookie сессии ставится с `sameSite: 'lax'`, без возни с межсайтовыми cookie;
- адрес сервера не надо нигде прописывать, в коде относительные пути.

Порядок в коде важен: в `backend/src/app.ts` сначала описаны ручки `/api`, потом раздача статики. Если поменять местами, запрос к API вернёт `index.html`, и клиент получит HTML вместо JSON.

### Где это разместить

| Где                           | Плюсы                                     | Минусы                                                              |
| ----------------------------- | ----------------------------------------- | ------------------------------------------------------------------- |
| **Render** (Free)             | Бесплатно, деплой из GitHub, умеет Docker | Засыпает после 15 минут без запросов, первый запрос ждёт ~50 секунд |
| **Timeweb Cloud**, **Amvera** | Российские, не засыпают                   | Платно, порядка 150–300 ₽ в месяц                                   |
| **Neon** (база отдельно)      | Бесплатный PostgreSQL                     | —                                                                   |

GitHub Pages не подойдёт: он отдаёт только статические файлы, Node и PostgreSQL там не запустятся. Репозиторий на GitHub всё равно нужен — для кода, пул-реквестов и проверки сборки.

Что прописать в переменных окружения при деплое: `DATABASE_URL`, `AUTH_SECRET` (длинная случайная строка), `NODE_ENV=production`.

**Перед защитой:** бесплатный Render засыпает. Откройте сайт за пару минут до показа, чтобы сервер успел проснуться. Запасной вариант — поднять всё локально: `npm run dev:nodb` работает без базы и без Docker.

## Что почитать в коде первым делом

1. `packages/shared/src/color.ts` — там объяснено, почему точность нельзя считать по RGB. Это главная содержательная часть проекта.
2. `packages/shared/src/api.ts` — контракт между фронтом и бэком.
3. `frontend/src/features/games/useGameSession.ts` — общий игровой цикл: один порядок действий на все игры.
4. `backend/src/games/repository.ts` — почему хранилище описано интерфейсом и что это дало тестам.
